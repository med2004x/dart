# Lesson 2: RPC and Serialization

## Objective

Build a minimal RPC (Remote Procedure Call) system with proper timeouts and retries, and solve Lesson 1's exact duplicate-request problem with idempotency — turning the previous lesson's abstract danger into a concretely handled case.

## Prerequisites

Lesson 1 (failure models — this lesson builds the first real mechanism addressing that lesson's core ambiguity), networking Lesson 1 (sockets/framing — RPC is a structured protocol built on exactly that foundation).

## Learn

**RPC: making a remote call look like a local one, syntactically — while remaining nothing like one, semantically.** An RPC framework lets you write `result := client.Call("Service.Method", args)` that looks like an ordinary function call, but under the hood serializes the arguments, sends them over the network (networking Lesson 1's framing), waits for a response, and deserializes the result. The syntactic convenience is genuinely useful, but it's also historically been a source of real bugs, because it can tempt developers into forgetting Lesson 1's fundamental point: a remote call can fail in ways a local call structurally cannot (network partition, remote crash, arbitrary delay) — RPC's local-call-like syntax doesn't remove those risks, it just hides them from the call site unless the developer actively accounts for them.

**Serialization.** Converting in-memory data structures into bytes for transmission (and back again on the receiving end) — this needs an agreed-upon format both sides understand (JSON, Protocol Buffers, or a custom binary format) and needs to handle **compatibility**: what happens when the client and server are running different versions of the code, with slightly different data structures? A well-designed serialization format supports adding new optional fields without breaking old clients/servers that don't know about them — a genuinely important, easy-to-get-wrong concern for any system that gets deployed incrementally (which is essentially all real systems, since client and server updates are rarely perfectly synchronized).

**Timeouts.** Since Lesson 1 established you can't wait forever for an ambiguous non-response, an RPC client needs an explicit timeout — some bound after which it gives up waiting and treats the call as failed, even though (per Lesson 1) this doesn't actually tell you whether the remote operation happened. Choosing a timeout value is a real tradeoff: too short, and you'll frequently time out calls that would have succeeded if you'd waited slightly longer (especially under real, variable network/processing latency); too long, and callers wait unnecessarily long to detect genuine failures.

**Retries and idempotency: solving Lesson 1's duplicate problem.** A retry after a timeout might duplicate an already-succeeded operation (Lesson 1's failure drill, restated). The standard fix: assign each request a unique ID (generated by the client, before the first attempt), and have the server track which request IDs it has already processed — if a retry arrives with an ID the server has already seen, the server returns the same result as before *without* re-executing the operation. This is what makes a request **idempotent** in practice — not because the underlying operation is naturally idempotent (appending to a list, from Lesson 1's example, is not naturally idempotent — appending twice differs from appending once), but because the request-ID-tracking mechanism makes repeated delivery of the *same* request produce only one effective execution.

## Attempt

1. Build a minimal RPC client/server (Go's built-in `net/rpc` package is a reasonable, quick way to get a working RPC mechanism without hand-rolling wire-format parsing, though you're welcome to build directly on networking Lesson 1's raw sockets/framing if you want the deeper exercise) with at least one method that takes an argument and returns a result.

2. Add a client-side timeout: if the server doesn't respond within a configured duration, the client call returns an error rather than blocking indefinitely. Test it by adding an artificial delay to the server's handler (longer than your configured timeout) and confirming the client correctly times out rather than hanging.

3. Implement the request-ID/idempotency mechanism from Learn: the client generates a unique ID per logical operation (not per retry — the same ID is reused across retries of the *same* logical request) and includes it in the RPC call; the server maintains an in-memory map of already-processed request IDs to their results, and for a request ID it's already seen, returns the cached result without re-executing the underlying operation.

4. Test the full scenario end to end: implement a non-idempotent server operation (e.g. "append to a list" from Lesson 1's example), have the client send a request, have the server process it successfully but have the client-side code simulate not receiving the response (e.g. deliberately ignore the first response to force a retry), have the client retry with the *same* request ID, and confirm — by inspecting the server's list state directly — that the item was appended exactly once, not twice, despite the client's retry.

## Verify

For step 4, report the server-side list's actual final contents after the simulated dropped-response-and-retry scenario, and confirm it contains exactly one instance of the appended item, directly proving your idempotency mechanism prevented the duplicate that Lesson 1's failure drill demonstrated as a real risk.

## Failure drill

Disable your step 3 idempotency mechanism (revert to the naive retry from Lesson 1's failure drill — no request-ID tracking) and rerun step 4's exact scenario. Confirm the item is now appended twice, reproducing the duplicate-write bug concretely, with your own server's state as the evidence, rather than only as an abstract concern from Lesson 1. Then explain, in your own words, precisely what specific piece of state (the server's request-ID history) is what separates the working version from the broken one — the retry logic itself didn't change between the two versions, only whether the server could recognize a retry as a retry.

## Transfer

gRPC (a common, production-grade RPC framework, built on HTTP/2 and Protocol Buffers) provides deadline/timeout propagation and structured error codes as first-class features, but does *not* automatically provide the idempotency mechanism from this lesson — that's still the application's responsibility to design and implement correctly, exactly as you just did manually. If TARDOC or any of your systems use an RPC-style internal API (even a REST API called internally between services counts, conceptually, for this purpose) for an operation with real side effects (charging something, sending a notification, modifying a record), describe whether that operation currently has any equivalent of this lesson's request-ID idempotency mechanism, and what a duplicate execution would actually cause if a client-side retry happened to hit it.

## Done when

Your RPC client correctly times out rather than hanging indefinitely on an unresponsive server, and you've directly demonstrated — with your own server's observable state, not just a warning read in this lesson — both the duplicate-write bug from naive retries and its fix via request-ID-based idempotency, and can explain precisely what state the fix depends on.
